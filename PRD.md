# SignalMonitor

## PRD v0.2

## Implementation status note

This PRD keeps the broader product direction, but the current self-hosted implementation is intentionally narrower:

- Implemented: events, errors, breadcrumbs, LLM calls, traces, spans, identify user/tenant traits, source-map uploads and stack resolution, HTTP uptime monitors, heartbeat monitors, simple alert rules, email/webhook notification channels, dead-letter operations, retention, backups, public OpenAPI docs, and the TypeScript/JavaScript SDK.
- Not implemented yet: stored log telemetry, ClickHouse analytical storage, product object storage for source maps, session replay, feature flag rollout, statistical experimentation, SaaS workspaces, billing, invites, per-project RBAC, native Telegram/Discord/WhatsApp channels, escalation policies, and on-call rotations.

When this document conflicts with `README.md`, `/docs`, `/sdk`, or `.claude/docs/*`, the implementation docs are the source of truth.

## 1. Product Vision

**SignalMonitor** is a proprietary observability and operational intelligence platform for digital products, APIs, workflows, and AI-powered applications.

The goal is to centralize, in a single environment, the key signals generated by systems:

```txt
product events
errors
breadcrumbs
traces
AI calls
costs
latency
sessions
users
tenants
workflows
alerts
```

The first version will focus on capturing and visualizing the essential signals needed to understand:

> What happened, who it happened to, where it happened, how long it took, how much it cost, and what the impact was.

## 2. Problem

Current products generate many important signals, but they are usually scattered across different places:

```txt
usage events
frontend errors
backend errors
workflow failures
automation logs
AI calls
cost per model
latency per step
user sessions
behavior by tenant
```

This makes it hard to answer simple questions such as:

```txt
Which user had an error?
Which tenant consumed the most AI?
Which prompt was the most expensive?
Which flow is slow?
Which workflow failed?
Which endpoint is unstable?
Which feature is most used?
Which part of execution caused the issue?
```

SignalMonitor solves this by creating a single observability timeline.

## 3. Objective

Build an internal platform to capture, store, query, and visualize operational and product signals across all systems.

The product should enable tracking of:

```txt
system health
product usage
technical failures
workflow executions
AI cost and performance
behavior by user
behavior by tenant
operational alerts
```

For now, the plan is organized into four phases.

## Phase 1: Telemetry Core

```txt

```

### Expected outcome

At the end of Phase 1, any system should be able to send signals to SignalMonitor in a standardized way.

## Phase 2: SDK and Product Integration

### Objective

Make it easier to integrate existing products with SignalMonitor.

### Capabilities

```txt
JavaScript SDK
track()
identify()
identifyUser()
identifyTenant()
captureError()
startTrace()
span()
breadcrumb()
llm()
flush()
```

### Usage example

```ts
signal.identifyUser("user_123", {
  email: "user@email.com",
  plan: "pro"
})

signal.track("dashboard_created", {
  source: "ai",
  charts_count: 6
})

signal.captureError(error, {
  area: "dashboard_generation"
})

signal.llm({
  provider: "openai",
  model: "gpt-5.5",
  prompt_name: "generate_sql",
  input_tokens: 1200,
  output_tokens: 300,
  latency_ms: 8400,
  cost_usd: 0.03
})
```

### Expected outcome

At the end of Phase 2, the main products should be instrumented with just a few lines of code.

Fields to mask:


### Suggested initial retention

```txt

```

### Expected outcome

At the end of Phase 4, SignalMonitor should be ready to operate multiple products with safety, predictability, and basic alerts.

## 12. Final Positioning

SignalMonitor should be seen as:

> A proprietary unified observability layer for digital products and AI systems, focused on events, errors, traces, costs, latency, users, tenants, and workflows.

The first version should avoid unnecessary complexity and focus on one core question:

> What happened in this flow, and what was the technical, operational, and financial impact?
