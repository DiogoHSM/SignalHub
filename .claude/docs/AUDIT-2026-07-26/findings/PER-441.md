## Achados

### F1 — [HIGH] Trait `eq` nunca casa com valores não-string (number/boolean) devido à coerção de texto no containment

- **Dimensão:** lógica/edge cases (valores não-string em jsonb containment — item explicitamente pedido no escopo)
- **file:line:** `packages/db/src/repositories/analytics-segment-compiler.ts:193-196` (branch `containmentEq`) e `:258-260` (`compileTraitLeaf` sempre passa `containmentEq: node.operator === "eq"`)
- **Evidência:**
  ```ts
  if (operator === "eq" && options.containmentEq) {
    const text = typeof value === "string" ? value : String(value ?? "");
    return sql<boolean>`${column} @> jsonb_build_object(${name}::text, ${text}::text)`;
  }
  ```
- **Por que importa:** todo trait `eq` (o único caminho pensado para usar o índice GIN `jsonb_path_ops` de `0044_profile_traits_gin.sql`) força o valor comparado para texto e monta `jsonb_build_object(name, "30")` — um JSON **string**. Traits são gravados preservando o tipo nativo do JSON recebido: `packages/telemetry/src/sanitization.ts` define `SanitizedValue = string | number | boolean | ...` e `identity-profiles.ts` grava `sanitizeValue(traits)` sem forçar string. Logo um trait `{"score": 30}` (number) ou `{"verified": true}` (boolean) nunca é igual, via containment, a `{"score": "30"}`/`{"verified": "true"}` — a condição `eq` falha silenciosamente (zero resultados) para qualquer trait numérico ou booleano, sem erro, sem log. Os operadores `gt/gte/lt/lte` (via `->>::numeric`) e `in` (via `->>` = ANY) continuam corretos porque extraem o valor como texto em vez de usar containment — só o `eq` de trait está quebrado.
- **Fix sugerido:** no branch `containmentEq`, construir o objeto de comparação preservando o tipo — `jsonb_build_object(name, value)` deixando o parâmetro bindado como number/boolean/string conforme o tipo de `value`, ou detectar o tipo de `value` e escolher entre construir jsonb com `to_jsonb($1::numeric)` / `to_jsonb($1::boolean)` / `$1::text` conforme o caso.
- **Cobertura de teste:** nenhum teste usa valor numérico ou booleano para trait `eq` (`analytics-segment-compiler.test.ts:100-105`, `repositories.test.ts` linhas 167-231 — todos usam `"enterprise"`/`"free"`, string). O bug não é pego por nenhuma suíte.
- **Confiança:** 0.9

### F2 — [MEDIUM] `updateAnalyticsSegment`/`archiveAnalyticsSegment` não escopam por `project_id`/`environment_id` (IDOR entre projetos) — pré-existente, mas nas rotas que este PR modificou

- **Dimensão:** segurança (IDOR entre projetos)
- **file:line:** `packages/db/src/repositories/analytics-segments.ts:211-240` (funções não tocadas por este diff — confirmado via `git diff` isolado nessas funções e `git show main:...` idêntico)
- **Evidência:**
  ```ts
  .where("id", "=", id)
  .where("archived_at", "is", null)
  // sem .where("project_id", ...) nem .where("environment_id", ...)
  ```
  Compare com as 3 funções irmãs no mesmo arquivo (`createAnalyticsSegment`, `listAnalyticsSegments`, `getAnalyticsSegment`), todas escopadas por `project_id`+`environment_id`.
- **Por que importa:** as rotas `PATCH /admin/analytics-segments/:id` e `DELETE /admin/analytics-segments/:id` (ambas tocadas por este PR para adicionar `validateAnalyticsSegmentDefinition`) repassam apenas o `id` da URL para essas funções — nenhum `projectId`/`environmentId` do payload é usado para restringir o update/archive. Um admin autenticado que conheça (ou adivinhe) o ID de um segmento de **outro** projeto pode atualizar sua definição ou arquivá-lo. `requireAdmin` é um admin global (não por projeto), então o impacto depende de o modelo de tenancy do console já assumir um único operador confiável cross-projeto — mas isso contradiz a assimetria com as demais funções do mesmo arquivo, que claramente pretendiam esse escopo. Não é uma regressão do PER-441 (o código já existia em `main`), mas é diretamente adjacente às rotas que este PR alterou e bate com o item explícito "IDOR entre projetos" do escopo de auditoria.
- **Fix sugerido:** adicionar `.where("project_id", "=", projectId).where("environment_id", "=", environmentId)` em ambas as funções, passando esses campos a partir da rota (que já valida `params`/`body`).
- **Confiança:** 0.6 (severidade real depende do modelo de trust do admin global do produto, não documentado explicitamente em `GUARDRAILS.md`/`ARCHITECTURE.md`)

### F3 — [MEDIUM] Segmentos definidos só por trait leaves nunca aparecem em `previewAnalyticsSegment`/`getAnalyticsSegmentActorIds` se o ator não tiver evento na janela

- **Dimensão:** fluxo de dados / lógica
- **file:line:** `packages/db/src/repositories/analytics-segments.ts:266-282` (`analyticsSegmentActorSubquery`) e `:293-320` (`previewAnalyticsSegment`)
- **Evidência:**
  ```ts
  return db.selectFrom("events")
    .select([actorColumn.as("actor_id"), sql<Date>`max(timestamp)`.as("last_seen_at")])
    .where("project_id", "=", segment.projectId)
    .where("environment_id", "=", segment.environmentId)
    .where("timestamp", ">=", from).where("timestamp", "<", to)
    .where(actorColumn, "is not", null)
    .where(predicate)   // <- o predicado do segmento (pode ser 100% trait, sem depender de eventos)
    .groupBy(actorColumn);
  ```
- **Por que importa:** o pool de atores candidatos vem sempre de uma agregação sobre `events` dentro da janela. Um segmento composto só por `trait` leaves (ex.: "plan = enterprise") depende, ainda assim, de o ator ter ao menos 1 evento no período — um usuário/tenant identificado com o trait certo mas sem eventos na janela nunca aparece no preview nem na contagem de atores, mesmo satisfazendo 100% da condição declarada. Isso é diferente do uso do predicado como filtro correlacionado em `listEvents`/`listSessionReplays`/`getEventPaths` (onde faz sentido exigir um evento, pois a query já é sobre eventos) — mas para "quantos atores este segmento tem" é uma discrepância semântica não documentada em `DECISIONS.md`/`ARCHITECTURE.md`.
- **Fix sugerido:** ao menos documentar a limitação; idealmente, para uma árvore sem nenhum leaf do tipo `event`, construir o pool de atores a partir de `user_profiles`/`tenant_profiles` em vez de `events`.
- **Confiança:** 0.55 (pode ser um trade-off aceito implicitamente, mas não está registrado como tal)

### F4 — [MEDIUM] Rotas de leitura (`/query/events`, `/query/session-replays`, `/query/events/paths`) não distinguem `SegmentDefinitionError` — retornam 503 genérico em vez de 400 nomeado

- **Dimensão:** erros / contrato de API
- **file:line:** `apps/api/src/routes/query.ts:1560-1567` (`handleListRoute`, usado por `/query/events` e `/query/session-replays`) e `:2263-2275` / `:2096-2107` (session-replays e event-paths handlers)
- **Evidência:**
  ```ts
  try {
    return sendListResult(reply, await run(filters));
  } catch (error) {
    if (isInvalidCursorError(error)) return reply.status(400).send({ error: "invalid_cursor" });
    return reply.status(503).send({ error: "query_unavailable" });
  }
  ```
- **Por que importa:** `analyticsSegmentActorFilter`/`compileSegmentDefinition` **revalidam** (`validateSegmentDefinition`) toda vez que um segmento salvo é usado como filtro (não há cache do resultado da validação feita na gravação). Se um segmento já persistido deixar de satisfazer os limites atuais (ex.: os limites `MAX_DEPTH`/`MAX_NODES` forem reduzidos numa versão futura, ou dado corrompido/migrado), a leitura lança `SegmentDefinitionError`, mas essas 3 rotas engolem qualquer erro em um catch genérico e devolvem 503 — violando o invariante "erros nomeados retornam 400, não 500". Hoje não é diretamente explorável (create/update já validam antes de persistir), mas é uma lacuna real de defesa em profundidade diretamente ligada às novas named errors que este PR introduziu.
- **Fix sugerido:** nos 3 catch blocks, checar `error instanceof SegmentDefinitionError` e responder `400` com `{ error: error.code }` antes do fallback genérico — mesmo padrão já usado em `admin.ts`/`validateAnalyticsSegmentDefinition`.
- **Confiança:** 0.55

### F6 — [LOW] Semântica de `neq`/`eq` para propriedade/trait ausente não é discutida (nem documentada) — informacional

- **Dimensão:** lógica/edge cases
- **file:line:** `packages/db/src/repositories/analytics-segment-compiler.ts:198-202`
- **Evidência:** `(column ->> name) <> text` — se a chave não existir, `->>` retorna `NULL`, e `NULL <> texto` é `NULL` (falso em `WHERE`). Ou seja, tanto `eq` quanto `neq` excluem atores onde a propriedade/trait não existe. Pode ser surpreendente para quem espera que `neq` inclua "campo ausente" como "diferente de X".
- **Por que importa:** não é um bug (é uma escolha de design defensável, e é o mesmo comportamento de `->>` em qualquer segmento v1 anterior), mas vale registrar/documentar explicitamente para não virar um ticket de suporte depois.
- **Confiança:** 0.4

### F7 — [LOW] `SegmentEventLeaf.property` aceita só uma condição por leaf — "multi-condição no mesmo evento" exige leaves separados, que não garantem correlação na mesma linha de evento

- **Dimensão:** lógica/edge cases (cobertura de AC — "multi-condição")
- **Evidência:** `SegmentEventLeaf.property?: SegmentPropertyCondition` é singular. Para expressar "evento X com propriedade A=1 E propriedade B=2 no mesmo evento", só dá pra compor dois leaves de evento diferentes num `group.and`, mas cada leaf vira seu próprio `EXISTS (SELECT 1 FROM events e WHERE ...)` independente — podem casar com linhas de evento **diferentes**, não necessariamente a mesma ocorrência. Isso é aceitável se a intenção do PER-441 era "atores que satisfazem múltiplas condições ao longo do tempo" (o que bate com a árvore and/or/not descrita na issue), mas se a intenção incluía "uma única ocorrência de evento com múltiplas propriedades", não é suportado hoje e não está documentado como limitação.
- **Confiança:** 0.5

## Sólido

- **Injeção — desenho sólido e testado de verdade.** Operador só resolve via mapa fechado (`COMPARISON_SQL`/`FREQUENCY_SQL`/`OPERATORS`), nome de propriedade/trait validado por regex de charset (`NAME_PATTERN`) como segunda barreira, e todo valor (inclusive arrays do `in`) passa pelo `sql` tag do Kysely como bind — nunca concatenado. Os testes de `analytics-segment-compiler.test.ts:141-188` realmente checam `.compile(db).sql`/`.parameters`, incluindo tentativas de `DROP TABLE` em nome, valor, valor de array e operador — não é teatro.
- **`sql.ref(outerRef)`/`sql.ref(actorColumn)` nunca recebem entrada do cliente.** Os três call sites em `telemetry-query.ts` (linhas 1625, ~1687, ~2137) passam literais fixos (`"events.user_id"`, `"session_replays.user_id"`, etc.), e `actorColumn` é sempre um dos dois literais `"tenant_id"`/`"user_id"` escolhidos por ternário — nunca uma string vinda de request.
- **Tenant isolation dentro das subqueries EXISTS/trait está correta.** `compileEventScopeConditions` e `compileTraitLeaf` incluem `project_id`/`environment_id` do `scope` (derivado do `segment` já buscado com escopo correto via `getAnalyticsSegment`) em toda subquery correlacionada — inclusive nas folhas de trait contra `user_profiles`/`tenant_profiles`.
- **Limites estruturais (profundidade ≤5, ≤32 nós, ≤8 filhos, `not` com exatamente 1 filho) são reais e testados**, incluindo os limites exatos (`allows exactly 5 levels of depth`) e a dupla camada schema (Zod, forma) + compilador (semântica) — um `not` com 2 filhos passa no Zod mas é pego pelo compilador.
- **Uso de EXISTS/count correlacionado em vez de `IN (array materializado em Node)` está completo para os 3 call sites do Phase 1** (`listEvents`, `listSessionReplays`, `getEventPaths`) — `getAnalyticsSegmentActorIds` continua existindo, mas só para preview/contagem administrativa, com `.limit(50_000)`.
- **NOT vira `NOT EXISTS`/`NOT (bool)`, nunca `NOT IN` com possível armadilha de NULL** — decisão correta e documentada no ADR (`DECISIONS.md`, 2026-07-26) como motivação explícita da migração.
- **Retrocompat v1 → v2 preservada corretamente**, inclusive o caso crítico citado no escopo: `propertyName` sem `propertyValue` mapeia para `operator: "exists"`, não `eq ""` (`upgradeDefinition`, testado explicitamente em `analytics-segment-compiler.test.ts:60-67`).
- **`recency.withinDays` negativo/zero é rejeitado em duas camadas** (Zod `min(1)` no schema de admin e `validateLeafShape` no compilador) — item do escopo coberto.
- **Documentação exemplar**: ADR novo em `DECISIONS.md` explica a troca de modelo, o motivo da containment (`@>`) para traits, e admite explicitamente a assimetria de performance entre `eq` (indexável) e `contains`/`gt`/`lt`/`neq` (não indexável) — raro ver o trade-off de performance documentado tão explicitamente antes de virar problema em produção. `DEPLOYMENT.md` também documenta o lock de `CREATE INDEX` (não-concorrente, pois migrations rodam em transação única) para operadores com tabelas de profile grandes.

## Validação adversarial (opus, 2026-07-26)

Postura: cético, default = REFUTADO salvo prova no código. Releitura na versão da branch (`git show diogohsm/per-441-...:<path>`), comparação com `main`, e — para F1 — prova empírica em Postgres 16 real.

### F1 — CONFIRMADO (mantém HIGH)

Todas as três pernas da cadeia foram verificadas no código, e a semântica SQL foi provada empiricamente, não deduzida:

1. **Traits chegam e são persistidos com tipo nativo.** `packages/telemetry/src/ingestion-schemas.ts:15-26,250-260` — `traits: jsonObjectSchema` = `z.record(z.string(), jsonValueSchema)`, e `jsonValueSchema` é a união `string | number | boolean | null | array | record`. `packages/telemetry/src/sanitization.ts:76-91` (`sanitizeValue`) só reescreve chaves sensíveis para `"[REDACTED]"`; o `return value as SanitizedValue` final devolve number/boolean intactos. `packages/db/src/repositories/identity-profiles.ts:25-31,41,64` grava `objectTraits(input.traits)` direto na coluna. Coluna é `jsonb` (`packages/db/migrations/0013_identity_profiles.sql:6,22`) — logo `{"score": 30}` fica number no banco, não string.
2. **O compilador força texto no containment.** `packages/db/src/repositories/analytics-segment-compiler.ts:193-196` — `const text = typeof value === "string" ? value : String(value ?? "")` e `${column} @> jsonb_build_object(${name}::text, ${text}::text)`. `:258-260` passa `containmentEq: node.operator === "eq"` para **todo** trait leaf. O valor vai bindado, mas com cast `::text`, então `jsonb_build_object` produz JSON **string**.
3. **Prova empírica** (Postgres 16, container efêmero):
   - `jsonb_build_object('score'::text, '30'::text)` → `{"score": "30"}`
   - `'{"score": 30}'::jsonb @> jsonb_build_object('score'::text,'30'::text)` → **false**
   - `'{"verified": true}'::jsonb @> jsonb_build_object('verified'::text,'true'::text)` → **false**
   - `'{"plan":"pro"}'::jsonb @> jsonb_build_object('plan'::text,'pro'::text)` → true (string funciona)
   - `('{"score": 30}'::jsonb ->> 'score') = '30'` → **true** (confirma que o caminho `->>` de `neq`/`gt`/`in` continua correto, isolando o defeito ao `eq` de trait)

Tentativas de refutação que **falharam**: (a) "talvez o valor não seja bindado com cast" — é, `::text` está explícito no template; (b) "talvez o Zod da rota só aceite string, então o problema seria só de tipo do value" — irrelevante: o defeito é determinado pelo **tipo armazenado** do trait, não pelo tipo do input (`segmentLeafValueSchema` em `apps/api/src/routes/admin.ts:584` aceita `z.number()` de qualquer forma); (c) "talvez a coluna seja `json` e `@>` nem compile, virando erro visível em vez de silencioso" — é `jsonb`, compila e retorna false silenciosamente; (d) "talvez o worker normalize traits para string" — não normaliza.

Mitigante registrado (não altera o veredito): o formulário do console só constrói definições v1 (`apps/console/src/components/EventInvestigationPanel.tsx:697-704` — `eventName`/`propertyName`/`propertyValue`), então trait leaves hoje só são criáveis via API. Ainda assim, é a Fase 3 do PR falhando silenciosamente (zero resultados, sem erro, sem log) para exatamente a classe de trait que a GIN/containment foi introduzida para servir, com teste possível (a suíte roda Postgres real via `@testcontainers/postgresql`, `packages/db/test/repositories.test.ts:1`).

### F2 — REBAIXADO para LOW (defense-in-depth; não é IDOR)

O fato de código é verdadeiro e pré-existente: `packages/db/src/repositories/analytics-segments.ts:199-240` (`updateAnalyticsSegment`/`archiveAnalyticsSegment`) filtram só por `id` + `archived_at is null`, e `git show main:packages/db/src/repositories/analytics-segments.ts` traz as duas funções **byte-a-byte idênticas** — não é regressão do PER-441. As rotas também não fazem escopo prévio: `apps/api/src/routes/admin.ts:2085-2090` chama `analyticsSegments.update(params.data.id, parsed.data)` e `:2114` chama `analyticsSegments.archive(params.data.id)`, sem `get` escopado antes — e o `updateAnalyticsSegmentSchema` (`:637-640`) faz `.omit({ projectId: true, environmentId: true })`, então a rota nem recebe o escopo para aplicar.

Mas **não existe fronteira de privilégio para atravessar**, o que derruba a classificação de IDOR:
- `requireAdmin` (`apps/api/src/routes/admin.ts:1510-1529`) autoriza por um único booleano global `user.isAdmin`; não há noção de projeto no gate.
- Não existe modelo de membership/RBAC por projeto em nenhum lugar (`grep -rl "project_members|projectMembers|membership" packages/db/src packages/db/migrations apps/api/src` → **zero arquivos**).
- Todas as rotas irmãs deixam o mesmo admin escolher livremente qualquer `project_id`/`environment_id` via query (`:2015-2040` list, `:2122-2150` preview). O admin que "atacaria" outro projeto já pode ler, criar e prever segmentos de qualquer projeto legitimamente.

Ou seja: o pior caso real é um admin global editar/arquivar um segmento de projeto diferente do que pretendia (erro de operação, não escalada). Vale corrigir por consistência com as 3 funções irmãs escopadas e por defesa em profundidade caso o produto ganhe admin por projeto — mas como achado de segurança de severidade média, refutado.

### F3 — REBAIXADO para LOW (lacuna de documentação, comportamento defensável)

Fato de código confirmado: `packages/db/src/repositories/analytics-segments.ts:266-282` monta o pool de atores sempre a partir de `selectFrom("events")` agregado na janela, e `previewAnalyticsSegment` (`:293-320`) deriva contagem e amostras dessa mesma subquery. Também confirmado que **isso é pré-existente**: em `main` as duas funções já liam de `events` (`git show main:...` → `selectFrom("events")` nas linhas 197 e 229).

Por que não é medium:
- A janela (`window`) é campo de primeira classe da própria definição do segmento (`AnalyticsSegmentDefinitionV2.window`, `resolveWindow` default `30d`), e o produto é um core de telemetria. "Atores do segmento" significando "atores com atividade na janela que satisfazem a condição" é uma definição coerente, não um bug — um ator sem nenhum evento em 30 dias não é um ator ativo do segmento.
- O caminho que realmente importa para o usuário — usar o segmento como **filtro** em `/query/events`, `/query/session-replays`, `/query/events/paths` — está correto para segmentos 100% trait: o predicado é aplicado como `EXISTS` correlacionado contra `user_profiles`/`tenant_profiles` (`analytics-segment-compiler.ts:246-266`), e a query externa já é sobre eventos/replays por natureza. Nenhum resultado incorreto é exibido ali.
- Superfície afetada é só o preview/contagem administrativo, e trait leaves ainda não são construíveis pelo console (só via API).

O que sobra é exatamente o que o próprio achado admite como fix mínimo: registrar a semântica ("pool de atores = atividade na janela") no ADR/ARCHITECTURE, já que o ADR novo em `DECISIONS.md` fala de trait leaves sem mencionar essa restrição. Isso é low.

### F4 — REBAIXADO para LOW (inalcançável hoje; nenhum invariante documentado violado)

Fato de código confirmado: `apps/api/src/routes/query.ts:1560-1567` (`handleListRoute`) e os handlers de session-replays/event-paths tratam só `isInvalidCursorError` e caem em `503 query_unavailable` genérico para todo o resto.

Mas a premissa do achado não se sustenta:
- **Nenhum invariante do projeto é violado.** Não existe `.claude/GUARDRAILS.md` neste repo (`ls .claude/` → só `design-v2/`, `docs/`, `memory/`, `work/`, `worktrees/`), e o que `ARCHITECTURE.md:303` documenta é justamente o escopo implementado: limites estruturais "reject pathological trees with a named error and `400` **before persistence**". O contrato prometido é o de escrita, e ele é cumprido (`admin.ts:648-661` + `normalizeDefinition`).
- **O caminho é inalcançável pela API.** Escrita valida duas vezes (`validateAnalyticsSegmentDefinition` na rota e `validateSegmentDefinition` dentro de `normalizeDefinition`), e o `segment_id` da leitura é só um id — nenhuma definição vinda do cliente chega ao compilador em tempo de leitura. Para disparar o cenário seria preciso apertar `MAX_DEPTH`/`MAX_NODES` numa versão futura ou corromper a linha fora da aplicação.
- Detalhe adicional que enfraquece o achado: se uma definição persistida inválida existisse, o throw aconteceria **antes** do compilador, dentro de `toSegment` → `parseDefinition` → `normalizeDefinition` → `validateSegmentDefinition` (`analytics-segments.ts:118-146`), ou seja no próprio `getAnalyticsSegment` — o mapeamento para 400 no catch da rota exigiria tratar o erro em mais de um ponto do que o fix sugerido supõe.
- O `503` genérico é a convenção uniforme deste arquivo (60+ ocorrências idênticas em `query.ts`), não uma lacuna introduzida por este PR.

Continua sendo uma melhoria legítima de defesa em profundidade — mas como nit (low), não como achado médio.
