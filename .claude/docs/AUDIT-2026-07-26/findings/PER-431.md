## Achados

### F1 — [ALTA] Mutação sem tratamento de erro: setPriority/setStatus falham em silêncio, sem toast, sem rollback, sem re-render de erro
- Dimensão: UI/robustez de mutação
- Arquivos: `apps/console/src/v2/screens/IncidentScreen.tsx:366` (`onClick={() => { void setStatus(s); setStatusOpen(false); }}`), `:882` (`onClick={() => { void setPriority(p); setPriorityOpen(false); }}`); implementação em `apps/console/src/v2/screens/useIncident.ts:458-480` (`setPriority`/`setStatus` fazem `await client.updateErrorGroupTriage(...); reload();` sem try/catch).
- Evidência: os handlers usam `void` para descartar a Promise. Se `updateErrorGroupTriage` rejeitar (rede, 403, 500), a exceção vira unhandled-rejection, `reload()` nunca roda, e o menu já fechou como se tivesse funcionado — o usuário não recebe nenhum sinal de falha e a UI continua mostrando o status/prioridade antigos sem indicar que a tentativa falhou. Não há teste cobrindo esse caminho (`useIncident.test.ts` e `IncidentScreen.test.tsx` só testam `mockResolvedValue`).
- Contraste dentro do mesmo PR: `AlertsScreen.tsx:812-820` (`handleAlertTriage`, não alterado por este diff mas coexistindo com a nova nota) já faz `const ok = await updateAlertEventTriage(...); if (!ok) ctx.pushToast("Failed to update alert")`. E o v1 (`apps/console/src/components/IncidentTriagePanel.tsx:28-40`) já tinha `try { ... } catch { setError("Triage update failed."); }` com `<p role="alert">`. Ou seja, o autor sabia fazer certo e aplicou em outro lugar do mesmo commit, mas não no recurso-título do ticket (priority/status no v2 Incident).
- Por que importa: é exatamente a pergunta do invariante "estado otimista com rollback em erro?" — a resposta real é pior que "sem rollback": é sem feedback de erro nenhum. Um operador pode achar que resolveu/priorizou um incidente crítico e na verdade a chamada falhou (rede instável, sessão expirada) sem perceber.
- Fix: envolver os dois `void setStatus(...)`/`void setPriority(...)` em `try/catch` com `ctx.pushToast(...)` no catch (mesmo padrão de `createExternalIssueDraft`/`linkExternalIssue` já existentes no próprio arquivo, linhas 260-312), e adicionar teste de rejeição em `useIncident.test.ts`.
- Confiança: 0.9

### F2 — [MÉDIA] Priority/Status não têm gate de permissão nem trilha de auditoria; inconsistente com Reassign no mesmo header
- Dimensão: autorização / auditabilidade
- Arquivos: `apps/api/src/routes/query.ts` — `requireHumanUser` (linhas ~1403-1417) guarda as 4 rotas (`handleErrorGroupStatusRoute` ~2465-2540, `handleSilenceIncidentRoute` ~2578, `handleTriageNoteRoute` ~2543, `handleErrorGroupIncidentRoute` ~2319); nenhuma chama `requireAdmin` (definido e usado só em `apps/api/src/routes/admin.ts:1430-1444`, ex. `/admin/users`). `apps/console/src/v2/screens/IncidentScreen.tsx` — botão Reassign tem `disabled={!canReassign}` (condicionado a `listUsers()` ter sucesso, que só funciona pra admin via `/admin/users` → `requireAdmin`), enquanto os botões Priority (linha ~866-873) e Status (linha ~347-357) não têm `disabled`/gate nenhum.
- Evidência: qualquer usuário humano autenticado (não-admin) pode mudar prioridade e status de um error_group via API e via UI v2, sem nenhuma checagem de papel e sem gravação em log de auditoria equivalente ao `feature_flag_audit` que existe pra feature flags (`ARCHITECTURE.md:315`). Busquei `admin_actions`/`audit_log`/`adminAction` em `query.ts` e `admin.ts` inteiros: zero ocorrências.
- Por que importa: é pré-existente no backend (não é regressão introduzida por este PR — `resolve()`/`reassign()`/`silence()` já usavam a mesma rota sem gate de admin antes), mas PER-431 é o primeiro release que expõe as 4 transições de status e as 4 prioridades livremente por dropdown pra qualquer humano autenticado no v2 (antes só existia um botão "Resolve" fixo). Isso amplia bastante a superfície de uso de uma rota sem controle de papel nem trilha de quem mudou o quê — vale uma decisão de produto explícita (ADR) confirmando que "qualquer humano pode fazer triage" é o desenho pretendido, já que o botão Reassign do mesmo header sinaliza o oposto ("Admin access required to reassign").
- Fix: não é bloqueante pro merge se for decisão consciente, mas recomendo registrar em `.claude/docs/DECISIONS.md` que triage (status/priority) é intencionalmente aberto a qualquer usuário autenticado (ou então adicionar gate), e considerar log de auditoria mínimo (quem mudou status/priority e quando) dado que já existe o padrão em `feature_flag_audit`.
- Confiança: 0.75

### F3 — [MÉDIA] Nenhuma validação de máquina de estados no servidor; PER-431 é quem passa a expor livremente as 4 transições via UI, sem coordenação com a regressão automática de ingestão
- Dimensão: integridade de dados / lógica de negócio
- Arquivos: `apps/api/src/routes/query.ts:344` (`errorGroupStatusSchema = z.enum(["open","investigating","resolved","ignored"])` — só valida pertencimento ao enum); `packages/db/src/repositories/error-groups.ts:618-657` (`updateErrorGroupTriage` aplica `patch.status = input.status` incondicionalmente, sem ler o status atual nem checar transição permitida); teste `apps/api/test/query.test.ts:3178-3199` (`it.each([...4 status])("accepts %s...")`) confirma que qualquer valor é aceito sem setup de estado prévio — comportamento intencional, não lacuna de teste.
- Regressão automática: `packages/db/src/repositories/error-groups.ts:369-467` (`upsertErrorGroupForOccurrence`, chamado do worker de ingestão, não da API) reabre um grupo `resolved` para `open` quando chega uma nova ocorrência com timestamp posterior a `resolved_at` (`shouldReopenResolved` via SQL `case when ...`). Esse caminho e o PATCH humano (`updateErrorGroupTriage`) escrevem na mesma linha `error_groups` por `UPDATE ... WHERE id/project/environment` sem nenhum controle de concorrência (sem coluna de versão, sem `WHERE updated_at = ...`) — são last-write-wins entre si, silenciosamente.
- Por que importa: não é regressão nova (a lógica de reopen e a ausência de state machine já existiam), mas antes do PER-431 o v2 só conseguia setar `status: "resolved"` (via `resolve()`/ConfirmButton); agora, via dropdown, dá pra setar `open`/`investigating`/`ignored` a qualquer momento, inclusive revertendo manualmente um grupo que acabou de regredir sozinho por ingestão — sem nenhum aviso de conflito. Combinado com F2 (sem gate de papel), o alcance prático desse gap cresce bastante neste PR.
- Fix: aceitável documentar como decisão consciente (per instrução do brief), mas recomendo pelo menos um ADR curto reconhecendo "sem máquina de estados server-side; last-write-wins entre reopen automático e triage manual é aceito", ou then adicionar validação mínima (ex.: bloquear settar o mesmo status atual como no-op silencioso, e/ou registrar `last_regressed_at` como contexto exibido ao operador quando ele reabrir manualmente um grupo pós-regressão).
- Confiança: 0.65

- **Reload pós-mutação consistente**: todas as mutações novas (`setPriority`, `setStatus`) seguem o padrão pré-existente de `reassign`/`silence`/`addNote`: `await client.updateErrorGroupTriage(...); reload();` — sem estado otimista, mas com refetch real após sucesso (quando há sucesso — ver F1 pro caminho de falha).

Não é lost update: é regressão desenhada e guardada por timestamp — uma ocorrência atrasada (timestamp < `resolved_at`) **não** reabre.
