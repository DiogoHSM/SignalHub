## Achados

**F1 — Sev: Medium — Dimensão: correção funcional — `apps/console/src/v2/screens/LlmScreen.tsx:136-147,195,205`**
O seed de `pendingFilters` para a seção `llm` traz seis campos (`tenantId, userId, provider, model, promptName, status` — ver `timelineNavTarget` em `UsersScreen.tsx:77-90`, que sempre popula todos eles a partir de uma linha de timeline LLM). Mas `provider`, `model` e `promptName` são lidos com `useState` **sem setter** (`const [provider] = useState(...)`, linhas 139-141), enquanto `hasSeededFilters` (linha 195) só olha `tenantId`/`userId`, e o botão "Clear filters" (linha 205) só reseta `tenantId`, `userId` e `callStatus`. Resultado: todo clique numa linha de timeline LLM a partir de Users deixa `provider/model/promptName` aplicados à query (`useLlm.ts` os repassa direto ao `listLlmCalls`) sem nenhuma forma de removê-los pela UI — o chip "Clear filters" aparece (porque `userId` sempre vem preenchido) e o operador acredita ter limpado o filtro, mas a lista "Recent calls" continua restrita ao provider/model/prompt herdados da navegação. Só um remount completo da tela (sair e voltar sem filtros) reseta. Fix: dar setter a `provider/model/promptName` e incluí-los no `onClick` do "Clear filters", ou refletir os três no texto do chip para não mentir sobre o que está filtrado. Confiança: 0.9.

**F2 — Sev: Medium — Dimensão: correção de UI/estado — `apps/console/src/v2/screens/UsersScreen.tsx:464-470`**
`<UserDetailPanel ctx={ctx} row={selectedRow} window={window} />` é renderizado sem `key` atrelada a `selectedRow.key`. Trocar de usuário selecionado (clicar em outra linha da lista) **não remonta** `UserDetailPanel` — o componente é o mesmo instance, só props mudam. Os estados locais `detailTenantDraft`/`appliedDetailTenantId` (linhas 203-204) e `signalType` (linha 205) persistem entre usuários diferentes. Se o operador aplica um filtro de tenant ou de signal type olhando o usuário A e depois seleciona o usuário B, o detail de B é buscado (`useUserDetail` recebe o novo `userId` correto) mas **já filtrado** pelo tenant/signal residual de A — sem nenhuma indicação visual de que esse filtro veio de outra sessão de navegação, o que pode fazer B parecer sem atividade/tráfego quando na verdade só está sendo filtrado por um tenant que não se aplica a ele. Fix: `key={selectedRow.key}` no `UserDetailPanel`, ou um `useEffect` que reseta os três estados quando `row.key` muda. Confiança: 0.9.

**F3 — Sev: Medium — Dimensão: correção funcional / UX enganosa — `apps/console/src/v2/screens/UsersScreen.tsx:373`, `useUsers.ts:132-134`, `packages/db/src/repositories/users-query.ts:449-463`**

Um usuário com o maior `errors` ou `llmCost` da janela mas fora do top-50-por-impacto **nunca aparece** ao clicar na aba "Errors" ou "LLM cost" — a UI não tem nenhum aviso disso (nenhum texto tipo "ordenado dentro dos 50 carregados"). É o comportamento já sinalizado no batch como follow-up de backend (PER-446 — sort/cursor no servidor), mas o gap de UX (nenhum disclaimer) não foi mitigado nesta unidade. ## Sólido

- **Mecânica one-shot correta e testada onde importa**: `navigate()` em `ConsoleShellV2.tsx:163-174` seta `pending` só quando `filters` é passado, senão `null` — um clique simples no `NavRail` (`onNavigate(section: NavSection)`, sem filtros, `NavRail.tsx:7-17`) sempre limpa qualquer seed pendente, mesmo que a tela de destino nunca chame `clearPendingFilters`. O remount via `key={seq}` (`ConsoleShellV2.tsx:363`, `seq` incrementado em toda chamada de `navigate`) garante que `useState(seed?.x)` nas três telas consumidoras (`ErrorsScreen.tsx:230-239`, `TracesScreen.tsx:853-855`, `LlmScreen.tsx:137-142`) sempre leia o payload correto na primeira renderização. Teste de integração real cobrindo Users → LLM (seed) → LLM (clique plano, seed limpo) em `ConsoleShellV2.test.tsx:578-654`.
- **`clearPendingFilters` chamado nas 3 telas alvo**: `investigate`/`traces`/`llm` (as únicas em `FilterableSection`) todas têm `useEffect(() => ctx.clearPendingFilters?.(), [])` no mount (`ErrorsScreen.tsx:244`, `TracesScreen.tsx:860`, `LlmScreen.tsx:147`). `users` não precisa consumir nada — não está em `SectionFilters` (`registry.tsx:38`), coerente com o fato de nada navegar *para* Users com filtro nesta unidade.
- **StrictMode double-invoke inofensivo**: `apps/console/src/main.tsx` usa `<StrictMode>`, que em dev duplica o efeito de mount/cleanup — mas `clearPendingFilters` é idempotente (`setPending(null)` quando já é `null` não gera novo render) e não roda em produção. Sem risco de corrida real.
- **Escopo e sessão nas rotas consumidas (pré-existentes)**: `handleUserListRoute`/`handleUserDetailRoute` (`apps/api/src/routes/query.ts:2222-2260`) chamam `requireHumanUser` antes de tudo, e `parseUserListFilters`/`parseUserDetailFilters` exigem `projectId`+`environmentId`+`window` (retornam `undefined` → 400 se faltar). Não modificadas por este PR, mas corretamente reaproveitadas pelo novo consumidor.
- **Sem XSS por trait**: nenhum `dangerouslySetInnerHTML`, `href` ou `mailto:` construído a partir de valor de trait em todo o diff (`git diff` completo grepado, zero ocorrências). Traits renderizam via `formatTraitValue` (`UsersScreen.tsx:42-51`) dentro de `<Kv>`/`<span>` — texto React, sempre escapado.
- **Navegação a partir da timeline é bem tipada e testada**: `timelineNavTarget` mapeia error/trace/llm para os três `FilterableSection` com testes unitários (`UsersScreen.test.tsx:193-224`) e testes de clique real por tipo (`UsersScreen.test.tsx:128-156`); `event` retorna `null` e a linha correspondente fica desabilitada (`UsersScreen.tsx:184-190`, testado em `UsersScreen.test.tsx:158-168`) — condizente com o comentário `PER-436 will map them`.
- **Race guard de fetch**: tanto `useUsers` quanto `useUserDetail` usam `genRef` para descartar respostas de requisições obsoletas (testado explicitamente em `useUsers.test.ts:129-148` com resolução fora de ordem).
- **`Apply filters` é opt-in, não input-on-every-keystroke**: busca/tenant na lista de Users só disparam fetch ao clicar "Apply filters" (`UsersScreen.tsx:420-425`, testado em `UsersScreen.test.tsx:170-177`) — evita um fetch por tecla digitada.

## Cobertura de AC

Escopo declarado da unidade: tela Users (lista + detail com traits/KPIs/timeline) e navegação com filtros no ScreenCtx (`pendingFilters`/`clearPendingFilters`) a partir da timeline de Users.

- Tela Users — lista (busca, tenant, sort, seleção, estado vazio/loading/erro): **entregue**, testado em `UsersScreen.test.tsx`.
- Tela Users — detail (identity profile, traits, KPIs, recent sessions, timeline com "load more" por cursor): **entregue**. Gap: troca de usuário selecionado não reseta filtros locais do detail (F2).
- Navegação com filtros para `investigate`/`traces`/`llm` a partir da timeline: **entregue e testado** por seção (seed consumido, `clearPendingFilters` chamado, chip de limpar filtro funcional para `investigate`/`traces`). Gap: o chip de limpar filtro em `llm` é parcial (F1) — não cobre `provider/model/promptName`.
- Navegação com filtros para `events` (a partir de linhas de timeline do tipo `event`): **explicitamente fora de escopo**, documentado inline como PER-436 follow-up (`UsersScreen.tsx:56,92`) — não é uma lacuna não-declarada.
- Sort/paginação server-side para a lista de Users: **fora de escopo, documentado como PER-446 follow-up** no batch — mas sem mitigação de UX (disclaimer) para o comportamento enganoso resultante (F3).
- Contrato `ScreenCtx`: mudança propagada corretamente para todos os consumidores existentes (10 arquivos de teste + 3 screens), sem quebra residual — só uma inconsistência estilística (F4).
