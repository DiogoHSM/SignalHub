## Achados

### F1 — [HIGH] URL completa do canal (segredo de fato para Slack/Discord) é devolvida sem redação pela API e renderizada sem máscara no console

- **Dimensão:** segredos / exposição de credenciais
- **file:line:** `apps/api/src/routes/admin.ts:1302-1306` (`redactNotificationChannel`), `apps/api/src/routes/admin.ts:3600-3617` (`GET /admin/notification-channels` devolve `channels.map(redactNotificationChannel)`), `apps/console/src/v2/screens/useAlerts.ts` (`url: c.type === "email" ? null : c.url`), `apps/console/src/v2/screens/AlertsScreen.tsx:475` (`{row.target}` renderiza a URL crua na lista de canais)
- **Evidência:**
  ```ts
  function redactNotificationChannel(channel: NotificationChannelRecord): Omit<NotificationChannelRecord, "secretHeaderValue"> {
    const { secretHeaderValue: _secretHeaderValue, ...safeChannel } = channel; // url NÃO é removida
    return safeChannel;
  }
  ```
  Teste da própria branch confirma o comportamento como esperado: `useAlerts.test.ts` — `expect(vm.channels[0]).toMatchObject({ target: "https://hooks.slack.com/services/T0/native", url: "https://hooks.slack.com/services/T0/native" })`.
- **Por que importa:** para um webhook genérico a URL pode ou não ser sensível por si só (a autenticação normalmente vem do `secretHeaderValue`, que este código já redige corretamente). Para Slack Incoming Webhooks e Discord Webhooks, **a URL inteira é o segredo** — qualquer um com a URL pode postar na integração sem nenhuma outra credencial. Este PR introduz exatamente esses dois tipos e reutiliza, sem ajuste, a mesma função de redação que só tira `secretHeaderValue`. Resultado: qualquer usuário com acesso de leitura à tela de Alertas do console (ou a quem acessar a resposta JSON de `GET /admin/notification-channels`) vê o token Slack/Discord em texto puro. Isso também contradiz a própria documentação atualizada neste PR (`UI-UX.md`: "the saved secret value is write-only and should never be displayed after submission") — a frase é verdadeira só para `secretHeaderValue`, dando falsa sensação de segurança sobre o campo que de fato importa para estes dois tipos novos.
- **Fix sugerido:** tratar `url` como segredo para `type in (slack, discord)` na resposta da API (ex.: mascarar tudo após o segmento de host, ou devolver só um `hasUrl`/últimos N caracteres, análogo ao padrão `hasSecret` já usado para `secretHeaderValue`) e ajustar o console para não renderizar a URL completa na lista/edição desses dois tipos.
- **Confiança:** 0.7 (o padrão de expor a URL já existia para `webhook` genérico antes deste PR — não é código novo — mas a superfície de risco muda de categoria quando a URL passa a ser, por design, o único segredo do canal; a PR tinha contexto suficiente para tratar isso e não tratou).

### F2 — [LOW] Nenhuma validação de domínio para canais Slack/Discord — qualquer URL pública é aceita sob esses tipos

- **Dimensão:** validação de input
- **file:line:** `apps/api/src/routes/admin.ts:597-609` (`webhookLikeNotificationChannelSchema`), `:1361-1368` (`validateWebhookUrl`), `:1430-1438` (`isValidNotificationChannelInput`)
- **Evidência:** o schema Zod para `slack`/`discord` é gerado pela mesma factory usada para `webhook` (`z.string().url()` + bloqueio de SSRF via `validateWebhookTargetUrl`), sem checar `hostname` contra `hooks.slack.com`/`discord.com`.
- **Por que importa:** um canal marcado como "Slack" ou "Discord" pode apontar para qualquer host público, entregando o payload formatado (`{text, blocks}` / `{embeds}`) para um destino arbitrário. O impacto é baixo porque a criação de canais exige admin (fronteira de confiança já assumida) e o SSRF continua bloqueado — mas quebra a expectativa implícita de "canal nativo" e pode ser usado para exfiltrar texto de alertas (nomes de regra, valores observados) para um endpoint externo sob o disfarce de "Slack".
- **Fix sugerido:** opcional — restringir `hostname` a `hooks.slack.com` para `slack` e a `discord.com`/`discordapp.com` para `discord`, ou documentar explicitamente que o rótulo é só cosmético.
- **Confiança:** 0.5

### F3 — [LOW] Ausência de idempotência estrutural nos reenvios para Slack/Discord (mensagens duplicadas em retry pós-timeout)

- **Dimensão:** retries / idempotência
- **file:line:** `apps/worker/src/alerts.ts:344-389` (`deliverWebhook`, loop de `attempts`)
- **Evidência:** cada tentativa reenvia o mesmo `body` sem qualquer chave de idempotência; para um `ETIMEDOUT` que ocorre **depois** que o Slack/Discord já processou a mensagem (só a resposta HTTP não chegou a tempo), o retry solto pelo `for (attempt = 1; attempt <= attempts...)` posta a mesma mensagem de novo.
- **Por que importa:** Incoming Webhooks do Slack e do Discord não suportam chave de idempotência (diferente de `chat.postMessage` com client-side dedupe), então esse comportamento é uma limitação estrutural da API deles, não um bug introduzido por este PR — o mesmo pipeline de retry já existia para o webhook genérico. Sinalizo porque o invariante do escopo pede "retries idempotentes" explicitamente e o único ponto novo (Slack/Discord) herda esse gap sem nota em `CONSTRAINTS.md`/`DECISIONS.md`.
- **Fix sugerido:** documentar a limitação (mensagens duplicadas são possíveis em timeout de rede pós-entrega) ou, se necessário, reduzir a janela de retry (`retryDelayMs`) para esses dois tipos.
- **Confiança:** 0.4 (informativo; pré-existente, não é regressão desta unidade)

### F4 — [LOW] Constraint `notification_channels_shape_check` da migration 0041 não tem teste negativo direto contra o Postgres

- **Dimensão:** testes / defesa em profundidade
- **file:line:** `packages/db/migrations/0041_notification_channel_slack_discord.sql:6-12`, `packages/db/test/repositories.test.ts` (novo teste "creates and updates native Slack and Discord notification channels")
- **Evidência:** o teste novo só passa por caminhos que o código de repositório já impede de violar a constraint (ex.: `updateNotificationChannel(db, slack.id, { url: null })` lança `webhook_url_required` **antes** de chegar no banco). Não há um `INSERT`/`UPDATE` cru via `sql\`...\`` que tente violar a constraint diretamente para confirmar que o Postgres também rejeitaria um estado inconsistente se o código de aplicação tivesse um bug.
- **Por que importa:** a constraint é a última linha de defesa contra dados inconsistentes (`type=slack` com `url IS NULL`, ou `type=email` com `url` setado); hoje sua eficácia real nunca é exercitada em teste, só inferida.
- **Fix sugerido:** um teste que insira via SQL cru contornando a camada de repositório e confirme que a constraint rejeita a combinação inválida.
- **Confiança:** 0.45

## Sólido

- **SSRF compartilhado sem bypass:** `deliverNotification` roteia `webhook`/`slack`/`discord` para o mesmo `deliverWebhook` (`input.channel.type !== "email"`, `apps/worker/src/alerts.ts:268-274`), que aplica `validateWebhookTarget` (bloqueio sintático) **e** `assertSafeResolvedAddresses`/`createValidatingWebhookLookup` (bloqueio pós-resolução DNS) antes de montar o body — não existe caminho novo que contorne a blocklist de redes locais/privadas/link-local/multicast/loopback/metadata. Confirmado lendo o código linha a linha; os dois novos tipos não introduzem branch alternativo.
- **Timeout explícito:** `requestHttpWebhook`/`requestHttpsWebhook` usam `setTimeout(timeoutMs)` + `request.destroy()`, sem exceção por tipo de canal.
- **Retry só para falha transitória:** `isRetryableWebhookStatus` (408/429/5xx) e `isRetryableWebhookError` (ECONNRESET/ECONNREFUSED/ETIMEDOUT/EPIPE/EAI_AGAIN) excluem explicitamente `"unsafe webhook target"` do retry — erro determinístico falha rápido, confirmado por teste (`errorMessage: "unsafe webhook target"` sem reattempt).
- **HTML de e-mail sem injeção:** `formatEmailHtmlBody` escapa todos os campos interpolados (`ruleName`, `severity`, `projectId/environmentId`, `observedValue/threshold`, `window`, `message`, e o próprio `href` do deep link) via `escapeHtml()`; teste dedicado injeta `<script>alert("x")</script>` na mensagem e confirma que o HTML final contém `&lt;script&gt;` e não `<script>`.
- **Header de e-mail não injetável na prática:** verifiquei diretamente (reprodução isolada com `nodemailer`'s `MailComposer`) que um `subject` contendo `\r\n` é dobrado/normalizado pelo próprio nodemailer (`Foo\r\nBcc: attacker@evil.com` vira `Foo Bcc: attacker@evil.com` na saída MIME, sem header extra injetado) — o invariante "headers injetáveis via nome de canal/regra" foi checado e não é explorável apesar de o schema (`z.string().trim()`) não remover `\r\n` do meio da string.
- **`secretHeaderValue` corretamente write-only:** `redactNotificationChannel` remove esse campo de toda resposta da API; `hasSecret` é o único indicador exposto.
- **Escopo admin:** todas as rotas `/admin/notification-channels*` continuam atrás de `requireAdmin`, inalterado.
- **Migration aditiva:** `0041_notification_channel_slack_discord.sql` só troca dois `CHECK CONSTRAINT`s (drop+add) para ampliar o enum de `type` e a regra de forma; não há perda de dado, segue o padrão já usado nas migrations anteriores do repositório.
- **Regressão de formato explicitamente travada:** teste "sends the raw alert payload unchanged for generic webhook channels (regression)" garante que `type: "webhook"` continua recebendo `JSON.stringify(payload)` bit-a-bit, sem passar pelos novos formatters.
- **Suíte de testes verde:** rodei a suíte completa contra o commit da branch — `api`+`db`: 272/272 passando; `worker`: 125/125; `console`: 1268/1268. `pnpm build` (todos os pacotes, incluindo `tsc --noEmit` de api/worker/db e `vite build` do console) e `docker compose config` também passam limpos.

## Validação adversarial (opus, 2026-07-26)

**Veredito F1: REBAIXADO — HIGH → MEDIUM.**

A exposição existe e é demonstrável, mas nenhuma fronteira de privilégio é cruzada, não há vazamento para logs, e o código de redação é **byte-a-byte idêntico ao de `main`** — a URL de canal já era devolvida em texto puro e já era renderizada na mesma linha do console antes desta branch. O delta real do PR é semântico (tipos novos em que a URL *é* a credencial) + a linha do VM que passou a incluir esses tipos no render. Isso sustenta MEDIUM (hardening de secret handling com risco lateral admin→sistema externo), não HIGH.

### Item 1 — A rota devolve a URL completa? Existe outra camada de redação?

**Confirmado, sem camada adicional.**
- `apps/api/src/routes/admin.ts:1291-1296` — `redactNotificationChannel` faz apenas `const { secretHeaderValue: _secretHeaderValue, ...safeChannel } = channel; return safeChannel;`. `url` passa intacta.
- Aplicada nas 3 rotas de leitura/escrita: `:3606` (`GET`, `channels.map(redactNotificationChannel)`), `:3631` (`POST`), `:3671` (`PATCH`).
- Console: `apps/console/src/v2/screens/useAlerts.ts:238` (`target: c.type === "email" ? c.emailRecipients.join(", ") : c.url`) e `:241` (`url: c.type === "email" ? null : c.url`) — nenhum mascaramento no VM.
- Render cru confirmado em `apps/console/src/v2/screens/AlertsScreen.tsx:475` (`{row.target}` dentro de `ChannelRow`, com `className="sh-faint sh-mono"` e `text-overflow: ellipsis` — truncamento **visual** por CSS, o valor completo está no DOM).
- Nenhum outro caminho de exposição: `git grep channel_url|channelUrl` em `apps/`+`packages/` retorna vazio; nenhuma rota de deliveries/attempts em `admin.ts` devolve `url`; `apps/api/src/openapi.ts` não documenta (nem exemplifica) as rotas de notification channels.

### Item 2 — Quem consegue ler? Existe rota não-admin?

**Só admin. Nenhuma rota não-admin expõe canais** — este é o principal motivo do rebaixamento.
- Todas as 4 rotas `/admin/notification-channels*` (`:3600`, `:3620`, `:3645`, `:3685`) abrem com `const admin = await requireAdmin(request, reply, options.auth); if (!admin) return reply;`.
- `requireAdmin` (`admin.ts:1441-1460`): `401 unauthenticated` sem sessão, `403 admin_required` quando `!user.isAdmin`.
- `git grep -l "notificationChannel|notification_channel"` em `apps/api/src` retorna **apenas** `routes/admin.ts` e `openapi.ts`. Não há rota alternativa.
- O modelo de usuários **tem** papéis (`packages/db/migrations/0001_initial.sql:8` — `is_admin boolean NOT NULL DEFAULT false`; `packages/db/src/repositories/users.ts:15,24,31`), portanto usuários não-admin existem — e são exatamente os que **não** conseguem ler a URL. Isso **refuta a formulação original do achado** ("qualquer usuário com acesso de leitura à tela de Alertas"): a lista de canais é admin-only, não read-only-user.
- Risco residual real (não nulo, o que impede REFUTADO): (a) instalação com mais de um admin — um admin lê o token Slack/Discord de outro e passa a poder postar no workspace **fora** do SignalMonitor, sem trilha no produto; (b) sessão admin roubada vira capacidade durável de post externo, porque o segredo é re-legível indefinidamente em vez de write-only; (c) screenshot/compartilhamento de tela da aba Alertas expõe o token.

### Item 3 — A URL aparece em logs estruturados ou mensagens de erro?

**Não. Verificado exaustivamente — negativo.**
- Todos os `console.error` do worker foram enumerados (`git grep "console\.(log|error|warn)"` em `apps/worker/src`): `alerts.ts:178,207,220,231,243,595`, `monitors.ts:113,147,156,168,530`, `backups.ts:378`, `heartbeat.ts:18`, `retention.ts:125`, `system-health-samples.ts:81`, `warehouse-exports.ts:263`. Nenhum recebe `channel` nem `channel.url` — só `rule.id` / `escalation.id` / `pending.eventId` + o objeto `error`.
- `deliverWebhook` (`apps/worker/src/alerts.ts:287-385`) **nunca propaga** exceção de entrega: todo `catch` retorna `DeliveryResult` com `errorMessage` passado por `sanitizeMessage` (`:620-622` → `sanitizePreviewText`). Logo o `error` logado em `alerts.ts:231` não vem do caminho de entrega HTTP.
- Nenhuma mensagem de erro construída embute a URL: `Webhook returned HTTP ${response.status}` (`:365`), `"Webhook DNS resolution failed"` (`:330` e `formatWebhookDeliveryError:530-532`), `"unsafe webhook target"` (`:328`), `"Webhook delivery timed out"` (`:299`/`:475`, criada pelo próprio código no `request.destroy`).
- O transporte é `http.request`/`https.request` nativo (`defaultWebhookRequest:403-415`), **não** `fetch`/undici — `fetchImpl` aparece só como tipo opcional em `alerts.ts:290` e não é usado em nenhum caminho. Isso importa: `undici` embute a URL completa em `TypeError: fetch failed` + `cause`, enquanto os erros do `http` nativo carregam no máximo host:porta (`getaddrinfo ENOTFOUND hooks.slack.com`, `connect ECONNREFUSED <ip>:443`, `socket hang up`) — nunca o path, que é onde vive o token do Slack/Discord.
- **Conclusão:** o invariante "logs devem redigir campos secret-bearing" **não é violado**. Se estivesse, o achado seria HIGH ou acima; é justamente esse resultado negativo que tira o multiplicador de severidade.

### Item 4 — Comparação com o comportamento pré-existente em `main`

**A URL já era devolvida em texto puro em `main`. O padrão foi herdado, não introduzido.**
- `git show main:apps/api/src/routes/admin.ts` → `redactNotificationChannel` é **idêntica** à da branch (mesmo destructuring, mesmo `Omit<..., "secretHeaderValue">`).
- `git diff main...d24a1030 -- apps/api/src/routes/admin.ts` tem 54 linhas e **zero ocorrências de `redact`** — a função e as 3 chamadas não foram tocadas pelo PR.
- `main:apps/console/src/v2/screens/useAlerts.ts:237,240` já fazia `target: c.type === "webhook" ? c.url : ...` / `url: c.type === "webhook" ? c.url : null`, e `main:apps/console/src/v2/screens/AlertsScreen.tsx:475` já era a linha do `{row.target}` cru. O PR só trocou o predicado `=== "webhook"` por `!== "email"`.
- Portanto o achado é, no plano do código, **questão de produto** (marcar `url` como write-only para `slack`/`discord`) e não regressão desta unidade. Contra-argumento que sustenta MEDIUM em vez de LOW: as duas linhas do VM que passaram a incluir os novos tipos **são** código deste PR, e o PR também adicionou a `UI-UX.md` a afirmação "the saved secret value is write-only and should never be displayed after submission" — verdadeira só para `secretHeaderValue`, falsa para o campo que virou o único segredo dos dois tipos novos. ### Item 5 — A URL entra em log por caminho de erro de entrega (ex.: `err.message` de fetch)?

**Não.** Coberto no item 3: transporte é `http`/`https` nativo (sem undici), `formatWebhookDeliveryError` (`alerts.ts:526-535`) reduz erros de DNS a string fixa e repassa `error.message` apenas para os demais códigos — e nenhum erro do `http` nativo contém o path da URL. Além disso todo `errorMessage` persistido passa por `sanitizeMessage`. Não há caminho em que o token Slack/Discord chegue a stdout/stderr ou à coluna de erro do banco.

### Severidade final e fix mínimo

**MEDIUM.** Não é HIGH porque: leitura restrita a `isAdmin` (`admin.ts:1441-1460`), zero exposição a usuário não-admin ou não autenticado, zero egress para logs, e o padrão é idêntico ao de `main`. Não é LOW porque: para `slack`/`discord` a URL é credencial bearer completa e permanece re-legível para sempre por qualquer sessão admin, contrariando o padrão `hasSecret` que o próprio arquivo já aplica a `secretHeaderValue` — e a doc adicionada neste PR afirma o oposto do comportamento real.

Fix mínimo (não bloqueia o AC): na resposta da API, para `type in (slack, discord)`, devolver `url` mascarada (host + últimos N caracteres) ou um `hasUrl` booleano análogo a `hasSecret`; ajustar `useAlerts.ts:238,241` para consumir a forma mascarada; e corrigir a frase de `UI-UX.md` para nomear explicitamente **qual** campo é write-only.
