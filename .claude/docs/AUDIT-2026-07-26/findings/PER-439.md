## Achados

### F1 — [HIGH] `breakdown_property` pode contar o mesmo ator mais de uma vez nos totais/steps principais (não só na série de breakdown)

- **Dimensão:** corretude do funil
- **file:line:** `packages/db/src/repositories/telemetry-query.ts:2049-2056` (`s0Cte`, `GROUP BY actor_id, actor_type, breakdown_value`), `:2166-2170` (`totalsResult` — `SELECT count(*) ... FROM chain` sem `GROUP BY`/`DISTINCT actor_id`), `:2177-2183` (`sampleResult` — mesma `chain`, `ORDER BY actor_id ASC LIMIT`)
- **Evidência:** `s0` agrupa por `(actor_id, actor_type, breakdown_value)`, não só por `actor_id`. Quando `breakdownProperty` é passado, `breakdown_value` vem de `properties ->> ${breakdownProperty}` calculado por evento (linha 2036). Se o mesmo ator tiver 2+ eventos do step 0 com valores distintos dessa propriedade dentro da janela (ex.: `plan` mudou entre duas ocorrências de `signup.started`), `s0` gera uma linha por combinação `(actor, valor)`, cada uma com seu próprio `t0`. A query de `totalsResult` (usada para `funnel.totals`/`funnel.steps`, o resultado "principal" exibido mesmo quando não se olha o breakdown) faz `count(*)`/`count(tN)` direto sobre `chain` sem desduplicar por ator — logo esse ator entra 2x (ou mais) na contagem de `entrants`/`actors` por step. O mesmo vale para `sampleActors` (pode listar o mesmo `actorId` duas vezes).
- **Por que importa:** o teste existente "breaks down funnel results by an event property" (`repositories.test.ts:10195-10236`) só usa atores com um único valor de propriedade cada (`user_pro` sempre `plan=pro`, `user_free` sempre `plan=free`), então nunca exercita esse caminho. O invariante do projeto ("atores contados uma vez por step") é violado silenciosamente sempre que `breakdown_property` é combinado com uma propriedade que varia por ocorrência do evento de entrada — um cenário realista (UTM, plano, feature flag no momento do evento). O número exibido no cabeçalho do funil (não só na tabela de breakdown) fica inflado sem qualquer sinal de erro.
- **Fix sugerido:** separar a CTE de totais/steps da CTE de breakdown: para `totalsResult`/`sampleResult`, agrupar `s0` só por `(actor_id, actor_type)` (ignorando `breakdown_value`, ou pegando o primeiro valor por `t0` mínimo absoluto) e usar uma segunda variação de `s0`/`chain` — agrupada também por `breakdown_value` — exclusivamente para a query de `breakdown`. Alternativamente, aplicar `count(distinct actor_id)` nos `countColumns` em vez de `count(*)`/`count(tN)`.
- **Confiança:** 0.7 (dedução analítica da leitura do SQL e do `GROUP BY`; não confirmei rodando um caso de teste ao vivo — evitei modificar arquivos rastreados fora do diretório de auditoria).

### F2 — [HIGH] Guard-rail `funnel_scope_too_large` ausente: cadeia `MATERIALIZED CTE` + `LEFT JOIN LATERAL` sem índice não tem cota de custo, e a doc nova supervaloriza a garantia de performance

- **Dimensão:** performance / DoS acidental
- **file:line:** `packages/db/src/repositories/telemetry-query.ts:2029-2088` (`buildFunnelChainCte` — `matched AS MATERIALIZED`, um `LEFT JOIN LATERAL` por step em `2067-2076`), `docs/HTTP-INGESTION.md` (linha nova: "aggregated in SQL (no per-actor row data leaves Postgres), so it stays cheap even for large event volumes")
- **Evidência:** `matched` é forçada a `MATERIALIZED` (sem índice no resultado). Cada `LEFT JOIN LATERAL` correlaciona por `m.actor_id = s0.actor_id AND m.name = steps[index] AND m.timestamp > prev` com um `min()` agregado — esse padrão (subquery correlacionada com agregado sobre uma CTE materializada) não é decorrelacionável pelo planner do Postgres em um join direto; a execução típica é um nested loop que reavalia a subconsulta (varredura de `matched`) uma vez por linha de `s0`. Custo ~ `|s0 atores| × (steps-1) × |matched|`. Não há `LIMIT`, cota de atores distintos, nem cota sobre `|matched|` antes de entrar nessa fase — só `MAX_FUNNEL_STEPS = 12` (linha 1944) e a janela fixa (`24h|7d|30d`, validada em `parseApmFilters`). Qualquer usuário autenticado (sessão humana já basta, não precisa ser admin) pode escolher dois nomes de evento muito frequentes num projeto com volume alto e período de 30d e forçar essa varredura repetida.
- **Por que importa:** é exatamente o gap que o próprio batch marcou como "mitigação sugerida, não-AC" — está confirmado no código que não há proteção alguma além do teto de 12 steps e da janela de tempo fixa. Em uma tabela `events` grande (o cenário-alvo do SignalMonitor como telemetry core self-hosted), essa query pode consumir CPU/memória do Postgres de forma desproporcional a partir de um input trivial do console, sem exigir volume de requisições (uma única chamada já é cara). Agrava o quadro: a doc adicionada nesta mesma PR (`docs/HTTP-INGESTION.md`) afirma que o funil "stays cheap even for large event volumes" — uma garantia que não foi validada (nenhum EXPLAIN/benchmark no diff) e que contradiz o próprio reconhecimento do batch sobre o guard-rail pendente.
- **Fix sugerido:** cota mínima antes de habilitar em produção: (a) `statement_timeout` dedicado para esta query, (b) um `funnel_scope_too_large` real — ex.: um `EXPLAIN (ANALYZE false)`/estimate de `|matched|` antes de rodar a query completa, ou um limite duro de linhas na CTE `matched` (`LIMIT` com erro 413 se estourar) — e ajustar a frase da doc para não prometer performance não medida.
- **Confiança:** 0.6 (fundamentado no modelo de execução conhecido do Postgres para `LATERAL`+CTE materializada com agregado; não medido com `EXPLAIN ANALYZE` num dataset grande real).

### F5 — [LOW] Migration 0041 usa `CREATE INDEX` simples (sem `CONCURRENTLY`) sobre a tabela `events`, a de maior volume de escrita do schema

- **Dimensão:** operação / migrations em produção
- **file:line:** `packages/db/migrations/0041_event_name_index.sql:1-2`, `packages/db/src/migrate.ts:52-77` (`db.transaction().execute(...)`, todas as migrations — incluindo a 0041 — rodam dentro de uma única transação)
- **Evidência:** `CREATE INDEX IF NOT EXISTS events_scope_name_time_idx ON events(project_id, environment_id, name, timestamp DESC);` sem `CONCURRENTLY`. O runner de migrations envolve todas as migrations pendentes em uma transação (`pg_advisory_xact_lock` + loop), e `CREATE INDEX CONCURRENTLY` é proibido dentro de bloco de transação no Postgres — ou seja, o próprio framework de migrations torna `CONCURRENTLY` inviável aqui sem uma mudança maior (migrations "não transacionais" fora do loop). Isso é um padrão pré-existente do repositório (outras migrations de índice, ex. `0017`, `0021`, seguem o mesmo formato), não algo introduzido s por esta PR isoladamente.
- **Por que importa:** `events` é a tabela de maior throughput de ingestão do SignalMonitor; um `CREATE INDEX` bloqueante (lock de escrita durante o build do índice) num banco de produção com uma tabela `events` grande pode pausar a ingestão por um período proporcional ao tamanho da tabela no momento do deploy/migração. Isso é uma limitação estrutural herdada do framework de migrations, não uma regressão desta unidade — mas como PER-439 é a primeira migration que toca especificamente `events` com esse padrão de índice composto (vs. tabelas menores em migrations anteriores), o risco relativo é maior que o de migrations anteriores.
- **Fix sugerido:** fora do escopo desta unidade isoladamente — mas vale abrir um item para o framework de migrations suportar passos não-transacionais (`CONCURRENTLY`) antes que `events` cresça o suficiente para isso doer num deploy real; documentar a limitação em `DEPLOYMENT.md`/`CONSTRAINTS.md`.
- **Confiança:** 0.6 (o mecanismo é verificável no código; o impacto real depende do tamanho da tabela `events` em cada instalação, que não medi).

### F6 — [LOW] Watch-item herdado (uso do índice 0041) permanece não comprovado por `EXPLAIN` ao vivo, mas a estrutura de predicados é compatível com o índice

- **Dimensão:** performance / verificação
- **file:line:** `packages/db/src/repositories/telemetry-query.ts:2037-2046` (predicados da `matched` CTE), `packages/db/migrations/0041_event_name_index.sql`
- **Evidência:** o índice é `events(project_id, environment_id, name, timestamp DESC)`. Os predicados da `matched` CTE, na mesma ordem das colunas do índice, são: `project_id = $1` (igualdade), `environment_id = $2` (igualdade), `name = ANY($3)` (lista curta, até 12 valores — compatível com scan por igualdade/bitmap por valor), `timestamp >= $4 AND timestamp < $5` (range na última coluna, alinhado com `DESC`). Estruturalmente esse é o caso ideal para o índice composto: PG deveria conseguir restringir por `project_id+environment_id+name` e depois varrer só o intervalo de timestamp por valor de `name`. Os predicados extras (`tenant_id = ...`, `segment` via `ANY(actor_ids)`) não fazem parte do índice e são aplicados como filtro residual pós-scan — não impedem o uso do índice, só adicionam custo de filtro.
- **Por que importa:** é o mesmo watch-item herdado do batch anterior — nunca foi fechado com um `EXPLAIN ANALYZE` real contra uma tabela populada. A análise estática aqui é favorável, mas não substitui a prova (o planner do Postgres pode preferir seq scan se a seletividade por `name` for baixa em relação ao tamanho da tabela, especialmente se as estatísticas do `ANALYZE` estiverem desatualizadas).
- **Fix sugerido:** rodar `EXPLAIN (ANALYZE, BUFFERS)` contra um `events` populado (mesmo que sintético, com volume realista) antes de considerar o watch-item fechado; registrar o plano em `DECISIONS.md` ou em um comentário de teste.
- **Confiança:** 0.55.

## Sólido

- **Nenhuma concatenação de identificador/operador vindo do cliente:** todo uso de `sql.raw`/`sql.ref` em `buildFunnelChainCte`/`getEventFunnel` é sobre strings controladas internamente — aliases `sN`/`tN` derivados só do índice numérico do loop (`1..steps.length`, limitado a `MAX_FUNNEL_STEPS=12`), e `segmentActorColumn` restrito por um ternário de duas opções fixas (`"user_id"`/`"tenant_id"`, nunca vindo direto do cliente). Os nomes de step (`steps`), a propriedade de breakdown (`breakdownProperty`) e os ids de segmento/tenant são sempre passados como valor bindado (`${...}` do template `sql`), nunca concatenados. Confirmado lendo `telemetry-query.ts:2025-2088` linha a linha.
- **`breakdown_property` tem defesa em profundidade:** além de ser bindado (não é identificador SQL — vira valor do operador `->>`), a rota valida contra `BREAKDOWN_PROPERTY_PATTERN = /^[A-Za-z0-9_.:-]{1,64}$/` (`apps/api/src/routes/query.ts:1101,1162-1165`), e há um teste explícito de tentativa de injeção (`breakdown_property=plan; drop table events` → 400) em `apps/api/test/query.test.ts`.
- **`ORDER BY` sempre fixo:** `ORDER BY actor_id ASC` na amostra e `ORDER BY 2 DESC` (posicional) no breakdown — nenhum nome de coluna vindo do cliente chega a um `ORDER BY`.
- **Escopo projeto+environment:** `matched` CTE sempre filtra `project_id`/`environment_id` como parâmetros bindados; `getAnalyticsSegment` (reusado para `segment_id`) também filtra por `project_id`/`environment_id` (`analytics-segments.ts:199-206`), então um `segment_id` de outro projeto não pode vazar atores.
- **Sessão humana exigida:** `handleEventFunnelRoute` chama `requireHumanUser` antes de parsear filtros (`apps/api/src/routes/query.ts:1876-1879`), consistente com o resto das rotas de `query.ts`.
- **Janela de conversão limitada pela janela do funil:** `parseConversionWindowSeconds` rejeita (`400`) um `conversion_window` maior que a janela `24h|7d|30d` selecionada (`APM_WINDOW_SECONDS`), evitando um bypass trivial do teto de tempo via esse parâmetro.
- **Ordem dos steps e timestamps estritamente crescentes:** cada `LEFT JOIN LATERAL` usa `m.timestamp > <alias anterior>.<coluna anterior>` (estrito), testado explicitamente por "requires strictly increasing step timestamps, ignoring an earlier out-of-order later-step event" — uma ocorrência prematura do step seguinte é corretamente ignorada.
- **Atores contados uma vez por step (caso base):** `count(*)`/`count(tN)` sobre `chain`, que tem uma linha por `(actor_id, actor_type)` quando `breakdown_property` não é usado (já que `properties ->> NULL` é sempre `NULL`, um único grupo por ator) — testado por "does not inflate funnel step counts on repeated events...".
- **Steps com nome repetido funcionam:** como cada step usa `m.timestamp > <timestamp do step anterior>`, um funil com o mesmo nome de evento duas vezes exige uma segunda ocorrência cronologicamente posterior — comportamento correto, não quebra.
- **Atores anônimos e sem chave:** identidade "auto" (`coalesce(user_id, tenant_id, session_id, trace_id)`) testada para atores só com `trace_id`, e eventos sem nenhuma chave são corretamente excluídos (`actor_key IS NOT NULL`).
- **Migration aditiva e idempotente:** `CREATE INDEX IF NOT EXISTS`, sem risco de quebrar uma instalação existente; framework de migrations com checksum (`migrate.ts`) impede alteração silenciosa do arquivo já aplicado.
- **Redundância de limite de steps:** `MAX_FUNNEL_STEPS = 12` e `steps.length < 2` são validados tanto na rota (`parseEventFunnelFilters`) quanto no repositório (`getEventFunnel`), defesa em profundidade mesmo que um segundo caller (fora da rota HTTP) chame `getEventFunnel` diretamente.

## Cobertura de AC

Não tive acesso ao Linear nesta sessão (MCP não autenticado) — avaliação feita contra a descrição da unidade fornecida no prompt do batch.

- **Funil calculado inteiramente em SQL, sem processar linha a linha no Node:** ✅ confirmado — `getEventFunnel` faz 2-3 roundtrips de SQL (totais, amostra, breakdown opcional), nenhuma linha de evento crua sai do Postgres; `.claude/docs/DECISIONS.md` documenta a motivação (corrigir um problema de OOM/performance da versão anterior que trazia linhas para o Node).
- **"Window functions":** ⚠️ parcialmente — o resultado final não usa window functions (`OVER`), usa CTE materializada + `LEFT JOIN LATERAL`; decisão documentada e funcionalmente adequada, mas diverge do nome da unidade (F4, cosmético).
- **Índice por name/janela:** ✅ entregue (`0041_event_name_index.sql`, `events(project_id, environment_id, name, timestamp DESC)`); estruturalmente compatível com os predicados da query (F6), mas sem prova por `EXPLAIN` ao vivo — watch-item continua aberto.
- **Guard-rail `funnel_scope_too_large`:** ✅ conforme combinado no batch, fica fora do AC desta unidade (mitigação sugerida, não obrigatória) — mas o risco de DoS acidental que ele mitigaria continua real e sem nenhuma outra proteção equivalente (F2).
- **Corretude (ordem, drop-off, janela de conversão, escopo tenant/segmento, atores anônimos):** ✅ testado e confirmado por leitura, exceto a combinação com `breakdown_property` (F1) e o isolamento cross-project (F3, gap de teste, não de código).
- **Testes verdes:** não executei a suíte ao vivo nesta sessão (evitei modificar/rodar build no worktree para não tocar em nada fora do diretório de auditoria); a leitura dos 7 testes de `getEventFunnel` + 4 testes de rota mostra cobertura real (não é teatro) das dimensões que cobrem, com as lacunas específicas listadas em F1/F3.

Resumo: a unidade entrega o funil funcional para os cenários testados, com o guard-rail de escopo grande explicitamente fora do AC (conforme combinado) — mas o risco de DoS que ele mitigaria não tem nenhuma outra barreira (F2), e existe um bug de corretude real e não coberto por teste quando `breakdown_property` é combinado com atores que têm múltiplos valores de propriedade no evento de entrada (F1).

## Validação adversarial (opus, 2026-07-26)

Método: releitura de `git show diogohsm/per-439-...:<path>` (`telemetry-query.ts:1944-2241`, `apps/api/src/routes/query.ts:1093-1175`, `packages/db/src/client.ts`, `packages/db/test/{repositories.test.ts,test-db.ts}`, `apps/api/test/query.test.ts`) **mais reprodução empírica** num Postgres 16 descartável (container `postgres:16-alpine`, porta 55439, destruído no fim; nenhum arquivo do repo modificado fora deste diretório). Postura: default = REFUTADO.

### F1 — CONFIRMADO (high)

Reproduzido em Postgres real, com o SQL reconstruído exatamente como `buildFunnelChainCte` o emite (2 steps, `breakdown_property = 'plan'`, sem conversion window). Dataset: `user_multi` com **dois** `signup.started` na janela (`plan=free` às 12:00:00 e `plan=pro` às 12:00:30) + um `project.created`; `user_single` com um `signup.started` (`plan=free`). Dois atores reais, um deles completa o funil.

- `totalsResult` (`telemetry-query.ts:2166-2170`, `count(*)` / `count(t1)`) retornou **`step0_actors = 3`, `step1_actors = 2`** — deveria ser 2 e 1. Entrants inflados em +50%, completed em +100%.
- `sampleResult` (`:2177-2183`) retornou **`user_multi` duas vezes** (linhas `free`/`t0=12:00:00` e `pro`/`t0=12:00:30`), ou seja `sampleActors` duplica o `actorId`, e o mapeamento TS (`:2185-2201`) não desduplica.
- Controle: a mesma query com `properties ->> NULL` (caminho sem breakdown) retornou **2 e 1**, correto — confirmando que o defeito é exclusivo do caminho com `breakdown_property` e que `properties ->> NULL` de fato colapsa em um único grupo por ator (a resolução de operador cai em `jsonb ->> text`, não dá erro de ambiguidade).

Não existe dedup em nenhuma camada: nem `distinct` no SQL (nenhuma das três queries usa `count(distinct ...)` ou `DISTINCT`), nem no TS. Nenhum dos 7 testes de funil (`repositories.test.ts:10032-10317`) cria um ator com dois valores de breakdown — o teste de breakdown (`:10195-10236`) usa `user_pro`/`user_free` com um valor fixo cada, e o teste de tenant/segmento (`:10268-10317`) também. Severidade **high** mantida: números do cabeçalho do funil (não só da tabela de breakdown) ficam silenciosamente errados, sem erro nem sinal.

### F2 — CONFIRMADO (high)

Refutação tentada e falhada em todas as frentes:

- **Sem `statement_timeout`**: `packages/db/src/client.ts` cria `new Pool({ connectionString })` sem nenhuma opção de timeout; `grep -r statement_timeout` no repo só encontra menções em docs de auditoria (inclusive uma recomendação já feita em `review/01-security-audit.md:364`, ainda não implementada). Nenhum `query_timeout` / `idle_in_transaction_session_timeout`.
- **Sem cota de linhas**: `matched` (`:2029-2046`) não tem `LIMIT`; o único `LIMIT` do caminho é o da amostra (`:2182`), aplicado **depois** de `chain` já ter sido materializada por inteiro. Totais e breakdown não têm limite algum.
- **Limites existentes são inócuos**: só `MAX_FUNNEL_STEPS = 12` (validado em dobro, rota `:1149` e repo `:2117`) e a janela `24h|7d|30d`; `parseConversionWindowSeconds` só *reduz* o escopo temporal. O rate limit global é `{ max: 1000, timeWindow: "1 minute" }` (`apps/api/src/app.ts:197`) — não é barreira para uma query que já é caríssima em **uma** chamada.
- **Custo medido, e é quadrático.** Benchmark no Postgres descartável (funil de 2 steps, sem breakdown, índice `(project_id, environment_id, name, timestamp DESC)` criado e `ANALYZE` rodado):

  | atores (= linhas de `s0`) | linhas em `matched` | tempo |
  |---|---|---|
  | 1.000 | 2.000 | 0,09 s |
  | 3.000 | 6.000 | 0,77 s |
  | 10.000 | 20.000 | 8,6 s |
  | 30.000 | 60.000 | **101,5 s** |

  3× de dados ≈ 11× de tempo — O(n²) confirmado, exatamente o `|s0| × |matched|` previsto no achado (o `LEFT JOIN LATERAL` com `min()` sobre CTE `MATERIALIZED` não é decorrelacionado; não há índice sobre o resultado materializado). Uma tentativa com 300.000 atores / 1M eventos foi **cancelada após 10 minutos sem terminar**. E `getEventFunnel` executa a cadeia inteira **2 vezes** (totais + amostra), **3 vezes** com breakdown — multiplicando os números acima.

  60 mil eventos numa janela é uma instalação minúscula pelos padrões de um telemetry core self-hosted; ou seja, o cenário de 100 s de CPU de Postgres por um único `GET /query/events/funnel` é atingível hoje, não numa hipótese distante.
- **Ator**: qualquer sessão humana autenticada (`requireHumanUser`, `query.ts:1876-1879`), não precisa ser admin.
- **Doc superestima**: `docs/HTTP-INGESTION.md` afirma que o funil "stays cheap even for large event volumes" — os números acima contradizem diretamente a frase, que deve ser corrigida.

Severidade **high** confirmada (e, se algo, subestimada): não é "DoS acidental teórico" — é degradação medida, sem timeout, sem cota, a partir de um input trivial do console. A pendência do guard-rail como não-AC não altera o risco operacional; o mínimo acionável é `statement_timeout` no pool (mudança de uma linha) antes de qualquer cota mais elaborada.
